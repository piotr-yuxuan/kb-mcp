## 4. Make the Merchant API safe to upgrade

| Key result | Type | Baseline | Target | Result | Score |
|---|---|---|---|---|---|
| Every new API key pinned to a dated version by 27 September (ENG-30) | C | | Done | Done on 21 September | 1.0 |
| Existing API keys pinned to a dated version | A | 0% | 30% | 9% | 0.3 |
| Migration guide for developers published | C | | Published | Draft only | 0.4 |

ENG-30 started in ENG Sprint 34 and the new-key work took most of the quarter. Without the upgrade assistant, merchants could only pin an existing key by asking support, which few did. The guide waited on decisions about how long older behaviour is supported, which [ADR-023](../architecture/adr-023-api-versioning.md) now settles. Both items carry over to the [Q4 2026 OKRs](okrs-2026-q4.md).

## What we learned

- **Ship the tool before the target.** Two of our weakest scores (existing keys pinned, dark mode opt-ins) measured adoption of something merchants could barely reach yet. In Q4, adoption key results follow the tool by at least a sprint.
- **Committed means committed.** Three committed key results missed. The migration guide should have been aspirational, or should have had an owner outside the engineering team.
- **Support is part of the launch.** Refund tickets fell fastest in the weeks after support updated its macros, not in the week of the launch.
